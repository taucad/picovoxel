# Results, 2026-10-25: the threaded build

.NET 10's multithreaded browser-wasm runtime (`WasmEnableThreads`), with the pthreads build of the PicoGK
runtime and oneTBB, at Emscripten 3.1.56. Headless Chromium 153 on the project's 4-core container, with a
pre-spawned pool of 8 workers. Voxel size 0.5 mm. Raw output: `threads-chromium.txt`.

The threaded runtime runs in browsers only: .NET refuses to start it in Node. Managed code runs on a worker, so
the task can block while oneTBB's workers run, and C# SDF callbacks are entered from those workers.

## Correctness

Both programs give the same bytes as the single-threaded build and native .NET. The gyroid sphere's digests are
`2b43725651c3733a` and `b8aa4cfd3b2b77f9`, and HeatX's 503 MB STL digest is `b9dac944dc434a69`, with the shared
float trigonometry.

## Speed

| Step                                  | wasm, 1 thread | wasm, threads, dlmalloc | wasm, threads, mimalloc | native, 4 cores |
| ------------------------------------- | -------------- | ----------------------- | ----------------------- | --------------- |
| HeatX task, s                         | 392            | 174                     | 168                     | 135 to 151      |
| HeatX volume and mesh, s              | 60             | 29                      | 18.4                    | 14.5            |
| Gyroid sphere mesh and properties, ms | 821 to 863     | 355 to 387              | 268 to 278              | 213             |
| 1M P/Invoke calls, ms                 | 58             | 125                     | 127                     | 70              |

With mimalloc, the threaded browser build runs HeatX within 1.24x of native on the same four cores, and 2.3x
faster than the single-threaded build. P/Invoke calls cost twice as much, because the threaded AOT build adds GC
safepoints; HeatX makes few enough of them for this not to matter.
