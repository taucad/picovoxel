# Upstream ledger

This register lists every defect, fix and improvement that picovoxel found in, or carries for, an upstream project. picovoxel is an unofficial community TypeScript/WebAssembly binding of LEAP 71's PicoGK; it is not affiliated with or endorsed by LEAP 71. Every fix listed here also ships inside picovoxel, so no picovoxel release waits for an upstream decision.

The keys (U1–U25 for runtime and dependency items, B1–B6 for the PicoGK C# library) are stable and are never reused. As of 2026-09-27, picovoxel has filed none of these items upstream.

## Status vocabulary

| Status       | Meaning                                                                                                                |
| ------------ | ---------------------------------------------------------------------------------------------------------------------- |
| `identified` | The defect or opportunity is described, with evidence, and nothing is implemented here                                 |
| `spiked`     | Implemented and measured in picovoxel                                                                                  |
| `pr-drafted` | The outward text (a pull request, or an issue or comment where the target takes those instead) and any patch are ready |
| `landed`     | Fixed in the upstream project                                                                                          |

Each row states whether the change moves output values. A row may name a blocker next to its status.

## Standing rule

Every patch picovoxel makes to an upstream dependency gets a row here in the same change that adds the patch, and the row cites the patch file by its path. A patch without a row, or a row that claims implemented and measured work without a patch file, is a defect in this document.

Patch files live in two places, explained in [README.md](README.md): `patches/<dependency>/*.patch` are applied to picovoxel's vendored build, and `upstream/*.patch` are proposals that are never applied locally.

## Evidence conventions

Unless a row says otherwise, measurements come from picovoxel's WebAssembly build on an Apple M2 Pro (12 cores, 32 GiB), Node 26.5.0 and emsdk 5.0.1, taken between 2026-07-26 and 2026-07-31. They are measurements on that machine, not guarantees. Test files named in a row are in this repository and run with `pnpm test`.

A patch offered upstream should carry evidence a maintainer can check on different hardware. For a change that claims identical output, that means run-to-run and single-thread against multi-thread identity at fine voxel sizes (0.7 mm and below): grid hash, volume as a hex double, active-voxel, vertex and triangle counts, and an order-independent mesh hash. For a change that moves values, it means geometric tolerances: corrected volume and surface area within 3%, bounds within one voxel, narrow-band distance change at most one voxel (mean at most 0.25 voxel), `tools::checkLevelSet` clean, and comparison with a closed form where one exists.

## Ours, not upstream

The multi-threaded build (`picovoxel/multi`) links mimalloc and the single-thread build links dlmalloc (`MALLOC=` in `scripts/build-pico-module.sh` overrides either). On 2026-07-26 and 2026-07-27, mimalloc made HeatX's multi-threaded construction stage 2.164× faster (CI 2.141–2.178) with output identical to dlmalloc in 64 comparisons; the raw samples are `bench/results/webgpu-v2/sk-0-exit-*.json`. It raised peak wasm heap 1.81× at 1.0 mm (0.866 → 1.567 GiB), about 1.3× at 0.5 mm; both allocators clear 0.5 mm and run out of memory at 0.4 mm.

A mesh corruption first blamed on mimalloc was picovoxel's own signed-shift heap read (U24 above): mimalloc only placed the staging buffer above 2 GiB, and a 400 MiB ballast reproduced the same corruption on dlmalloc. After the fix, mimalloc output is byte-identical to the dlmalloc single-thread build at 0.5, 0.6 and 0.7 mm (5 runs each, 2026-07-27). Nothing here is filed upstream.
